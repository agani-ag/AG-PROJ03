A plain-language guide

Where your code runs: the browser or the server

The same task can run in two different places. Where it runs decides what it is allowed to do — and it is the single idea behind why some things only work with a backend.

First, three words

Server, browser, and the two “sides”

People use these words all the time, but they name simple things. Here is each one in a sentence.

🖥️

A server is just a computer that is always on, waiting for requests and sending back answers. It sits in a data centre somewhere. When you run your Flask app, your own laptop is acting as the server — other programs send it requests and it replies.

🌐

A browser is the app a person opens — Chrome, Edge, Firefox. It downloads a web page from a server and shows it. It also runs the page’s JavaScript on the visitor’s own machine, inside a locked, careful sandbox.

↔️

“Client” means whoever is asking — almost always the browser. So client-side = code that runs in the visitor’s browser, and server-side = code that runs back on your server, out of sight. That’s the whole vocabulary.

How a page reaches you

One request, one reply

Every website is this loop, repeated. The browser asks; the server answers. Nothing more mysterious than posting a letter and getting one back.

💡

The key fact: the browser only ever has what the server chose to send it. Anything the server kept to itself — passwords, secret keys, private logic — the visitor never receives, and so can never see or change.

The two sides, side by side

Same code, very different powers

Move a piece of code from one side to the other and its abilities change completely — not because the code changed, but because where it runs changed.

◐ Client-side

Runs in the browser

On the visitor’s machine, in full view

  • The visitor can read every line (View Source, F12)
  • The visitor can pause it, change it, or skip it
  • Runs on the visitor’s device, so it costs you nothing
  • Works with things only the visitor has: camera, files, location
  • Must obey the browser’s safety rules
◑ Server-side

Runs on the server

On your machine, hidden from the visitor

  • The visitor never sees the code, only the result
  • The visitor cannot change how it decides anything
  • Can safely hold secrets — passwords, API keys
  • Can call any other service, with no browser restrictions
  • But it must be running, and every request passes through it
🏠

An everyday picture: client-side is your front garden — anyone walking past can look and touch. Server-side is the locked room inside your house — people only get what you hand out through the door. You’d keep your keys in the locked room, not on the garden wall.

What each side can and can’t do

The browser is powerful, but not private

The browser can do a great deal — but it can keep no secrets, and it can be trusted with no decision the visitor might want to cheat.

The browser is great for…

  • Anything the visitor is allowed to see anyway
  • Instant reactions — buttons, menus, form checks as you type
  • Using the visitor’s camera, microphone or chosen files
  • Simple tools that work offline, with no server at all
  • Calling services that openly allow browser access

The browser cannot…

  • Hide a secret — a password or key in the page is readable
  • Be trusted for a check the visitor could just skip
  • Set the real price, the real permission, the real result
  • Freely call services that block browsers (most of them)
  • Pretend to be anyone else — it carries the visitor’s identity
🔑

The rule in one line: if it must stay secret, or if it must be trusted, it belongs on the server. Everything a hidden key or an unskippable check protects is lost the moment you put it in the browser.

The exact thing that puzzled you

“The server can call the API. The browser calls the same API — and it fails.”

This feels wrong at first. It is the same address, the same request. Yet from a backend it works, and from a web page it’s blocked. Here is why, with no mystery left in it.

The reason is not the API and not your code. It’s who is making the call. A backend is a plain program with no rules over it. A browser is a guarded space, because it holds the visitor’s logins and cookies — so the browser refuses to let a page quietly read data from another website unless that website openly says “browsers may call me.” That permission is called CORS, and it is checked by the browser, never by the API.

🛡️

Why the browser is so strict: imagine you’re logged in to your bank in one tab. You open a stranger’s website in another. Its code runs in your browser, where your bank cookies live. Without this rule, that code could quietly read your bank balance. The browser blocks it to protect you. A backend has none of your cookies, so there is nothing to protect — and no rule.

What actually happened with the GST portal

These are the three things a browser runs into that a backend never does — the real reason the pure-HTML version couldn’t fetch GST details.

1

The browser asks permission first

Before sending the real search, the browser sends a quiet “may I?” check to the portal. The portal answers no. So the real search is never even sent.

Blocked before it starts
2

You can’t sneak around it

Dodging that check means changing how the request is labelled — and then the portal rejects it for being the wrong kind. There’s no clever way through from the browser.

No workaround
3

The captcha can’t be linked to the search

The portal ties the captcha to a private cookie. The browser refuses to attach that cookie to a call to another site, so the search never matches the captcha.

Cookie withheld
✓

The backend hits none of these walls

Python (or your Flask app) sends the request straight out, keeps the cookie, and reads the reply — because none of the browser’s rules apply to it. That is exactly why the Flask version works and the pure-HTML one can’t.

Works
📌

Two things people always get wrong: “blocked” doesn’t mean the API is safe — anyone can still call it with Python or a tool like Postman. And CORS doesn’t protect the API; it protects the person using the browser. Your AWS and Cloudinary pages work in the browser only because those services chose to allow it. The GST portal didn’t.

How to decide, every time

Three questions pick the side for you

Before you build a feature, ask these in order. If any one is a yes, it has to live on the server.

1

Does it need a secret — a password, a private key, a token no visitor should hold?

2

Must the result be trusted — a login, a price, a permission the visitor must not be able to fake?

3

Does it call a service that won’t allow browsers — like the GST portal?

If all three are no, the browser is a fine home — it’s faster, cheaper, and needs nothing running. If any is yes, put it on the server. That’s why your login demo needed a backend to be safe, why the keys-in-the-page version was risky, and why GST only works through Flask.
